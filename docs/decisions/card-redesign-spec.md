## 4. 数据映射（关键：哪些字段有、哪些缺）

| 卡片元素 | 数据来源 | 状态 |
|----------|----------|------|
| title | `content_items.title` | ✅ 现有 |
| 栏目 | `sources.title`（如「OpenAI 官方 News」） | ✅ 现有。原型里的「AI Agent 情报」「Go 生态」正是栏目化的信源名 |
| emoji 前缀 | 按 `sources.type` 派生，或存 `sources.config` | ⚠️ 需定：建议按 type 派生（rss/exa/tikhub_xhs），避免新字段 |
| 来源站点 | `content_items.url` 域名 | ✅ 可派生。**Exa/聚合源下与栏目不同**（栏目=「Exa: Anthropic 动态」，站点=各新闻站），这正是两者分开的意义 |
| 相对时间 | `content_items.published_at` | ✅ 现有（需「今天 / N 天前」格式化） |
| ⚡ 分数 | `deliveries.score` | ✅ 现有。注意契约 §17：该分是**个性化相关分**，跨期不可比；落库存原始分、排序用有效分——**展示用原始分** |
| 一句话洞察 | cardgen LLM 生成 | ⚠️ 需改 prompt（当前产出是标题复述） |
| 正文 | cardgen LLM | ✅ 改 prompt 结构 |
| 为什么与你有关 | cardgen LLM | ✅ 现有 |

**结论：无需新增数据概念**——「栏目」用 `sources.title` 即可，不必等信源插件化。

## 5. 实现要点

1. **cardgen prompt 重写**：产出三段——①一句话洞察（**不得复述标题**）②正文段落 ③为什么与你有关。
   保留既有「证据纪律」段（delivery 48 编造事故的修复）与注入防护段，二者是硬约束不得删。
   不再由 cardgen 拼 `[阅读原文]`（改为按钮，由构卡函数确定性生成——"挂链接留给代码"的原则不变）。
2. **`BuildDeliveryCard` 签名扩展**：现为 `(bodyMD, deliveryID, state)`，需要 title/subtitle/score/url。
   注意契约 CRITICAL：**workflow 包不得 import feishu**，构卡经函数注入——扩展签名会改动注入契约，
   需同步更新 workflow 侧的函数类型定义。
3. **误判语义保留**：去掉的只是按钮**入口**，`misjudged` 动作本身保留——
   👎 = `not_interested`，form 提交 = `misjudged` + `detail`（原因文本）。
   这样数据模型语义不变，**Gate ③ 仍可测**（点 👎 → 填原因 → 提交）。
   契约 §0「misjudged 定义：这条不该推给我」与输入框「哪里不对？」语义一致。
4. **form 提交是新回调类型**：现有 `card.action.trigger` 处理 button callback，
   form submit 的 event 结构不同，需在 `onCardAction` 扩展分支。
5. **幂等与最新为准**：沿用 M5 既有语义——态度可改、追加式事件日志、重复点幂等 toast。
6. **状态行措辞**改为「已记录」（对齐设计）。

## 6. form 回调结构（2026-07-16 已验证）

查 SDK `oapi-sdk-go/v3@v3.9.9` 的 `event/dispatcher/callback/model.go:30-40`，
Vane 已在用的 `CardActionTriggerEvent` 走的 `CallBackAction` 结构**原生支持 form**：

```go
type CallBackAction struct {
    Value      map[string]interface{} `json:"value"`       // 提交按钮自带的 value（放 vane_action + delivery_id）
    Tag        string                 `json:"tag"`
    Name       string                 `json:"name"`        // form 容器的 name
    FormValue  map[string]interface{} `json:"form_value"`  // form 提交：{input_name: 用户输入}
    InputValue string                 `json:"input_value"` // 单 input 场景的值
    Options    []string               `json:"options"`
    Checked    bool                   `json:"checked"`
}
```

**结论：无需换 SDK 或改订阅**。form 提交复用现有 `card.action.trigger` 通道，
在 `onCardAction` 里按新的 `vane_action` 值分流即可，`FormValue` 取用户填写的原因文本。

实现约定：
- 提交按钮 value 带 `vane_action: "fbr"`（feedback reason）+ `delivery_id`（**字符串**，
  沿用 §10.1 既有约定：JSON number 经 SDK 会变 float64，大 id 有精度隐患）。
- 原因文本从 `FormValue` 取，**长度上限 500**（对齐原型的 `0/500`），超长截断而非拒绝。
- 与既有按钮回调一样，`value` 只当线索——动作合法性、归属一律以服务端库内为准。

# 附录 A：聚合卡改版（2026-07-18 原型定稿，Boss 真人验证）

> 本附录**推翻了正文第 1 节的「聚合卡方案被单条卡取代」**。
> 07-15 定稿选单条卡时，聚合卡原型（10:44、11:33）确实被否；07-18 Boss 重新提出
> 「一个任务一张卡、任务内多情报聚合、多任务用顶部颜色+emoji 区分」，
> 经 lark-cli 原型 v1→v4 迭代 + 真人点击验证后定稿为下述形态。
> **正文第 1 节保留不改**（那是 07-15 当时的真实结论，不是错误记录）；以本附录为准。

## A.1 形态（原型 v4，`om_x100b6a82956f20acb2af647bc3f8450`）

```
header: template=<按任务着色>  title="{emoji} {任务名} · 今日 N 条"
        subtitle="见微 Vane · {节奏} · 按相关度排序"
body:
  ┌ 每条情报 ─────────────────
  │ **{标题}**　⚡{分数}
  │ {平台emoji} {栏目} · {域名} · {相对时间}
  │ {解读正文}
  │ 原文链接：[{截断显示}]({完整URL})
  │ [👍] [👎]
  └ hr 分隔
```

## A.2 三处与单条卡的实质差异

**① 🔍 深挖从卡面移除。** 依据是生产数据：21 条反馈里 deep_dive 只被点过 2 次
（interested 7 / not_interested 6 / question 4 / deep_dive 2 / misjudged 2），
而它是全场最重的动作（质量档 AgentModel、150s 异步预算、1600 max_tokens）。
聚合卡一屏 N 条，每条挂三个按钮 = 3N 个按钮，最贵且最低频的动作不该与最轻的平铺同权。
**能力本身保留**（feedback/deepdive.go 不动），入口移到 agent 对话侧
（追问 question 被点 4 次、是 deep_dive 的两倍，说明用户本就更习惯用嘴问）。

**② 「阅读原文」按钮 → 可见的原文链接文本。** Boss 原话：「看不到 url 是从哪里来我会没有安全感」。
机器生成的卡片里，一个不显示目标地址的跳转按钮无法被用户校验。

**③ 链接按结构截断，不按字符数。** 规则：**路径全留，query 省略成 `?…`**，
路径本身超 100 字符再硬截。真实数据实测（库内最长 URL 297 字符）：

| 案例 | 原长 | 显示 |
|---|---|---|
| Anthropic RSS（全是 HubSpot 多层编码追踪参数） | 297 | 48 |
| 小红书（`xsec_token` 是访问票据，非追踪参数） | 138 | 62 |
| Claude 文档（本就无 query） | 64 | 64（一字不动） |

为什么优于按字符数截：域名与路径是判断来源的唯一依据，必须完整；被省的 query 要么是
追踪垃圾、要么是人类读不了的票据。且**无需维护「哪些参数是追踪」的白名单**——
全省略即可，也就不存在误删 `xsec_token` 把链接搞坏的风险。

## A.3 链接渲染的硬约束（实测得来，违反即静默坏链）

**必须写成 `[{截断显示}]({完整URL})`，href 逐字符保留原 URL。**
**卡内绝不能出现裸的截断 URL 文本**——飞书会自动把它识别成链接，而 `...?…` 结尾是无效地址，
点击直接废掉。原型 v3 「点不动」的真因正是这个（当时误判成 markdown 链接写法有问题，
探针实测后才定位到是演示段落里的裸文本）。

**测试必须用带票据的小红书 URL 断言 href 逐字符相等。**
用 RSS/文档类 URL 测这个 bug 是**恒真的**——它们丢掉 query 照样能打开，
即便 href 被截断污染也看不出来。只有 `xsec_token` 丢了就打不开的链接才能证伪。
（探针 v1 用 Anthropic 链接就是这个错，Boss 当场指出「你要用小红书的链接」。）

## A.4 👎 误判 form 的定位方案（2026-07-18 三方案评审定稿：每条独立 form）

单条卡时代一卡一内容，form 提交天然对应那条；聚合卡需 form (a) 提交到正确 delivery
(b) 渲染在该条下方 (c) 不重置其他条状态。做错的后果是静默错记（对 B 条说推错、记到 A 条）。

**定稿：方案 1——每条内容各自持有条件渲染的 form，name 按 delivery_id 唯一化**
（form=`fbr_{id}`、input=`reason_{id}`、submit=`submit_{id}`）。关键依据：

- 卡片状态本就**从 DB 派生**（feedback/state.go：CardState 每次点击查库重建整卡），
  聚合只是把"查 1 条"变"查 N 条"，定位天然由 name 后缀 + value 双通道携带；
- **当前 form 的 name 是硬编码固定值**（card.go:190-210），N 条 form 必然重名——
  这正是串条的物理路径，唯一化 name 直接消灭它；
- 被否方案的实锤：全卡单 form 违反"渲染在该条下方"且目标会静默跳变（用户层错标概率最高）；
  不做 form 走对话会让**历史单条卡上现存 form 的提交无人接**（静默丢弃踩红线），
  且给 misjudged 信号加打字税。

**从否掉的方案吸收两点**：提交后 toast 带该条标题回显；**条数封顶 + 构卡后体积硬校验**
（超限拆卡，不静默截断）。

**实施前修两点**（评审要求）：FormValue 取值的 fallback 仅限 `Action.Name=="submit_reason"`
（历史卡兼容），新卡 keyed 取值失败必须 fail loud——否则 detail 静默丢失；体积校验进构卡函数。
